[DESIGN] These scenarios derive tests from the [workflow bodies](../../business-flow.md). All are planned cases, not completed acceptance, unless the execution note explicitly names an existing test run. Every row is marked from-requirement or recommended-by-risk. A row label applies to its preconditions, steps and expected result; tests for designed-only workflows are blocked until that workflow and its contract exist. (docs/REST-API-DATABASE-DESIGN.md; domain workflow citations)

## Synthetic fixtures

[INFERRED] Use two synthetic tenants A/B and distinct employees E1/E2, never real HR data. This follows the tenant risks in ml/confidence-service/confidence/api.py#Evidence and the absent Java tenant handlers. For calendar tests choose an explicit UTC fixture, Monday 2026-10-26, shift 09:00–17:00 and grace ten minutes; this is test data, not an adopted tenant policy. For balances choose entitled ten, carried two, used three, pending one (available eight). For ML use the exact PRESENT/PHONE_LEFT/SPOOFED dictionaries in ml/confidence-service/tests/test_service.py. Use valid IDs of the type the eventual contract adopts; Python currently accepts plain strings.
